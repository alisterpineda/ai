# implement evals

`claude plugin eval` cases for `/swe:implement`. Each case's `fixture.sh` sources the plan suite's `tally.sh`, which builds a small Python repository (`tally`, standard library only, tests run with `make test`) and defines the settled top-words spec. `review-loop` builds from a plan for that spec, and `group-steps` and `resume-slice` from plans of their own. The run is the slash command, once, and the graders read the trace, the final message, and the files it leaves. The repo-wide eval conventions (models, graders, sandbox) are in the root `CLAUDE.md`.

| Tag | Cases | What they check |
|---|---|---|
| `review`, `build` | `review-loop` | The one full run: build a two-step plan for the spec, kept in a gitignored `.scratch/`, then review and fix. The review is `swe:code-review-core` in 1 to 7 subagents, given the plan and, with no `--review-effort`, started at medium effort and called with `--effort medium`, none of them or of the reviewers in the background. The run ends on implement's own report, with its `Review:` and `Review model:` lines, not on the review's. An uncommitted `tally/stats.py` with a planted divide-by-zero, which no unit touches, is deferred as in the tree before the run and left as it was. The `Commit:` line follows the review: a sha when it ended clean or with nothing left to fix and no finding unfixed, else `not committed:` with the reason. Neither `tally/stats.py` nor the plan is ever staged, and nothing is staged with `git add .` or `-A`, amended, reset, or pushed. The deferred finding is also appended to the plan under `## Open findings`, dated and with the commit's sha or `uncommitted`, and the report's `Open findings:` line counts it. The marks follow the commit: when the run commits, both steps' first lines in the plan end ` Done: <date>, <sha>.` and the report says they were marked; when it doesn't, no step is marked and the report says the steps are still unmarked. |
| `review`, `build` | `review-fix` | The fix-and-review-again path. An uncommitted edit to `tally/counter.py`, the file the build changes, holds a planted `distinct_words` that counts every word. The run changed that file, so the finding is its to fix: the planted line is gone while `distinct_words` itself stays (the spec doesn't ask for it, but removing the user's code is their choice), a second review runs, called with `--serious-only` where exactly one review, the first, is called without it, and the `Review:` line counts at least one finding fixed. The run changed a file that already held uncommitted edits, so it makes no commit and the `Commit:` line says `not committed:`. |
| `review`, `build` | `review-rename` | A staged rename. A one-step plan renames a module and its tests "by `git mv`", which stages both renames. The run uses `git mv`, the review still runs, called with `--uncommitted` so it reads the whole change and not the index alone, and the `Commit:` line follows the review as in any other run, never naming staged changes or a skipped review. |
| `review`, `build` | `review-staged-start` | Changes staged before the run. The index holds a staged edit to the `Makefile`, which the plan's one README step doesn't touch. The review runs, with `--uncommitted`. The run makes no commit, since a commit would take the staged file along: the `Commit:` line says `not committed:` and names what was staged before the run, nothing is staged or unstaged, and the plan's step stays unmarked. |
| `review`, `build` | `review-flags` | `--review-model opus --review-effort low` reach the review: its subagent starts on that model and effort, the engine is called with `--model opus --effort low`, and the report's `Review model:` line names both. |
| `build` | `group-steps` | Grouping. A four-step plan built with `--no-review`: steps 1 to 3 add functions to the same two files and step 4 adds a module in files of its own. The prompt's context asks for every step to go to a worker, since the session otherwise builds steps this small itself and starts none. The run starts fewer workers than steps, on Sonnet at medium effort, the delegate model and effort for workers on an Opus or Fable session, since no flag names another, builds all four steps, and its report counts four units built and has a table with a `Group` column. |
| `build` | `no-review` | `--no-review` builds the spec, starts no review, stages and commits nothing, and hands over the `/swe:code-review` command. |
| `build` | `resume-slice` | Resuming a sliced plan. A three-slice plan built with `--no-review`, whose first slice's step is marked `Done:` with its code committed. The run builds the second slice's two steps and nothing else: `top_words` is as the fixture left it, the third slice's `tally/cli.py` does not exist, the report's `Built:` line counts 2 of 2 units and names slice 2, its `Review it:` command carries `--slice 2`, and its `Next slice:` line names slice 3. In the plan, the first slice's mark is unchanged and no other step is marked, since nothing was committed. |
| `args`, `quick` | `args-unknown-flag` | `--review`, the removed implement's flag, stops the run with the flags it takes, before any edit or subagent. |

The fix rule's judgment (which findings need the user's choice) has no case: the findings a review confirms on code the run has just written vary from run to run, so a grader has nothing fixed to check. `--no-commit` has no case either: it would cost a full build and review to check one flag, and `review-fix` already covers a run that reviews and then leaves the work uncommitted. No grader reads the plan and the final message together, so `review-loop` checks that the plan's marks are all there or all absent, and that the report's account of them fits its `Commit:` line, not that the plan and the report agree.

## Run

```
cd plugins
claude plugin eval . --eval-dir swe/evals/implement --scaffold --ablation none -j 3 \
  --model opus --judge-model opus --allow-tools Bash Write Edit
```

Add `--tag quick` for the case that stops before building.

- `Bash` is granted unrestricted because building runs the project's checks and the review runs its snapshot script. In `review-loop` the `no-git-writes` grader catches every git write but the commit and its staging by name; `review-fix` and `no-review` have a `no-commit` grader.
- `review-loop`, `review-fix`, `review-flags`, `review-rename`, and `review-staged-start` each run a build and up to seven reviews, so they are the slow, costly cases, about $1 to $2 a run.
